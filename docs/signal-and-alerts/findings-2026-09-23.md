## TL;DR

There are three separate problems. Only one of them is a routing (identity) problem in the bridge.

| # | What | Explains | Where it happens |
|---|---|---|---|
| **A** | **Station frame error on live station `ATS-6`.** From 2026-09-23 ~06:00Z, whole cycles are computed in a wrong station frame. The prisms are the right prisms, but every coordinate is rigidly rotated/tilted/shifted. Same thing on 09-08 → 09-15 with the opposite sign. Still happening on 10-03. | The **09-23 event** (all sites) | Station software (resection), not the bridge |
| **B** | **Point name ↔ physical prism mismatch at the station.** Two point names are taught on one prism, or ATR locks onto a neighbouring prism. Ingestion routes faithfully by name. | The **~8.9 m flip-flops** (SAVYON_LIVING 3, NAVON 23/24) | Station / GeoMoS config. Hexagon era and live era |
| **C** | **`ats-device-map` errors.** Swapped and crossed manual mappings, two devices into one sensor, map entries pointing at **deleted** sensor docs. | Silent wrong-sensor writes since 08-27, plus invisible data | Bridge + UI map edits + `cleanUnconfirmedSensors` |

The bridge's fallback routing (`findAtsSensor` by `atsDeviceId`) was **not** involved. Every `ATS-6-*` device had a map entry from 08-26/27 on, so the fallback never ran for these devices. Also, the fallback is an exact match, not a fuzzy one.

**Correction to the plan:** the 09-23 event covers **6** projects, not 4. JCTS_JAFFA_68 (h5 points) and JTCS_MERCANTIL (h3) are fed by the same station.

## 1. Context: which systems write to these sensors

- Until **2026-08-21** the JTCS prisms (`MAC = PRISM%ATS1%H…`) were fed by **Hexagon email ingestion** (`scanin-svc-hexagon-ats-ingestion`, `FirestoreService.PushDataAsync`: `where MAC == "PRISM%{group}%{point}"`, `.First()`). These samples have absolute `Easting/Northing/Height` and a `runId`.

The bridge routes these by `ats-device-map/{deviceId}` (`scaninHandler.processAtsSample` → `findOrCreateAtsSensor`). On **08-26/27** the map entries were edited by hand to point at the legacy Hexagon sensors, so the live data continues their history. These samples have `source: "ats_live"`, local `e/n/u` in metres and `de/dn/du_mm` relative to the station's own baseline.
- One station (`ATS-6`, 44 devices) feeds **6 projects**: NAVON_HOUSE (h0), SAVYON_OFFICE (h2p1/h2p2), SAVYON_LIVING (h2p3–h2p5), MERCANTIL (h3), JAFFA_68 (h5), NEVIIM 61 (h9).

### 2.2 Evidence: same prism, wrong frame

Payload vs. target doc for three affected prisms. All are `source: ats_live`, written by the bridge within 1–30 min of measurement:

| Sensor (doc) | Device | 09-23 00:0xZ cycle (dE/dN/dH mm) | 09-23 06:0xZ cycle | 09-24 03:0xZ cycle |
|---|---|---|---|---|
| NAVON "2" `ANoVhBf3RoXv6HGCMkBX` | `ATS-6-h0p1b` | 1.7 / 2.2 / 2.7 | **−188.2 / −792.5 / 473.5** | 1.9 / 1.4 / 4.7 |
| SAVYON_LIVING "18" `sen-prism-prism_JTCS_H2_3E` | `ATS-6-h2p3g` | −0.3 / −0.9 / 1.2 | **−1227.8 / −892.5 / 389.1** | n/a |
| NEVIIM "3" `sen-tilt-prism_JTCS_NEVIM61_2B` | `ATS-6-h9p2b` | 1.7 / 2.4 / 0.7 | **−3.9 / −880.8 / 544.6** | 2.0 / 1.1 / 2.4 |

Each device still writes to its mapped doc, and nothing in the routing changed. The values change for every point in the cycle at the same moment.

I fitted a 3D affine transform from the last good cycle (09-23 00:02Z) to the first bad one (06:02Z) over 34 points:

```
M = [ 0.99993  0.01022 -0.00580 ]   t = (-359, 0, -2) mm
    [-0.01022  0.99992 -0.00133 ]
    [ 0.00578  0.00138  0.99998 ]   residuals: median 0.6 mm, max 1.6 mm
```

That is a **rigid** transform: ≈ 10.2 mrad (0.59°) azimuth, ≈ 5.8 mrad + 1.4 mrad tilt, and −0.36 m translation. Every point fits to about 1 mm. The station measured the right prisms and transformed them with a wrong instrument→site transform. The 12:02Z cycle gives the same M. The shift grows with distance from the station: Δu is ≈ 68–87 mm at 14 m (h5) and ≈ 610–630 mm at 118 m (h2p1). That is why the plan saw "0.1–1.2 m", and why it is not an identity error.

`scanin-fw-ats-monitoring/docs/movement-resection-guide.md` describes exactly this failure: *"A wrong or poorly centered reference observation can corrupt the transform and therefore every monitored coordinate derived from it."* The station's own suspect check doesn't catch it. A rigidly wrong frame is perfectly repeatable, so the re-measurement and next-cycle confirmation both agree.

## 3. BR-0.2: the ~8.9 m flip-flops (root cause B)

Hexagon samples carry absolute coordinates, so for each sample I could check which physical prism was measured.

**SAVYON_LIVING "3"** (`sen-prism-prism_JTCS_H2_3F`, MAC `H2P3F`):
- Up to 05-24 04:07Z its position is (229 341.8, 10 019.0, 92 442.7) mm.
- From the **05-24 07:08Z** run on it reads (238 213.6, 9 902.8, 95 159.5). That is within **1 mm** of SAVYON_OFFICE "1" (`QLRep16jW8WOQdRM25LZ`, MAC `H2P2F`), which was measured in the same run (07:07:34Z).
- Δ = (+8 871.8, −116, +2 716.8) mm, which is exactly the "8 866 / −113 / 2 717" step `level-shifts.ts` reports.
- It flips back on 07-30 and again on 08-13 (`level-shifts.ts`).
- In the live era, `ATS-6-h2p3f` is **still** the same prism as `ATS-6-h2p2f` (`ats-crossmap.ts`: d = 1 mm to H2P2F's position).

**NAVON "23" / "24"** (`…_H0_12A` / `…_H0_12B`):
- On 07-06 → 07-10, "24" (H0P12B) reads (223 644.4, 57 467.0, 90 467.1). That is the same prism as NAVON "2" (H0P1B, 223 644.0, 57 467.3, 90 466.8), measured 30 s apart in the same run.
- On 07-08 20:27Z, "23" (H0P12A) jumps from (214 950, 54 856, 90 390) to (223 546, 57 703, 88 638). That is the position H0P1B/H0P12B had in May. Δ ≈ 8.6 m E, 2.8 m N.
- So three names (H0P1A, H0P1B, H0P12B, later H0P12A too) rotate over two or three physical prisms about 8.6–9 m from the H0P12 pair.

**Other duplicate prisms** (two names, one physical prism, both in Hexagon data and live):
- H0P7A = H0P7B
- H0P9A = H0P9B
- live `h0p10b` = `h0p11b`
- live `h2p5b` = `h2p5d`

**Mechanism.** The station's point list has names whose taught direction leads ATR to a neighbouring prism. It can also have two names on one prism. Both GeoMoS (Hexagon) and our ATS software then report that prism under the given name. Both ingestion paths route by name/device ID exactly: Hexagon by `MAC`, the bridge by `deviceId`. So the data lands in the "right" sensor for the name and the wrong one for the physical point. The ~8.9 m is just the spacing between those specific neighbouring prisms on the facade.

**Not the cause:**
- Bridge fallback routing: not used for these devices, and it is exact.
- Cross-station name collisions: no two stations share a device ID. `ATS-5-*` is DeVinci only.
- The Hexagon `MAC` collision with the inactive test project `בדיקת שקיעות`: 8 duplicate MACs, e.g. `PRISM%ATS1%H0P10A`. `.First()` returns the NAVON doc because `sen-prism-PRISM_…` sorts before `sen-prism-prism…`. It's a latent risk but didn't cause this.

**Masking via `initial-value`.** Several of these sensors have initial values that absorb metre-level offsets. For example NAVON "24" has E 8 727.4, N 3 009.9, TwoD 9 232. NAVON "18" has H 2 471.7, "14" has H 1 897.5, "11" has E −610 and H −1 651, and "4" has H 763.9. These look like someone set a new zero after an identity jump. The adjusted chart then looks normal while the sensor tracks a different prism.

**Affected ranges (B), from `level-shifts.ts --days=180` plus position checks:**
- SAVYON_LIVING "3": 05-24 07:08Z → 07-30, and 08-13 → present (live `h2p3f` = H2P2F's prism).
- NAVON "24": ≤ 05-01 → present (same prism as H0P1A/H0P1B, and as H0P12A in live).
- NAVON "23": 07-08 20:27Z → 07-10 (Hexagon), and live from 08-26 (2.7 m from its Hexagon position, matching nothing).
- NAVON "2": live from 08-26 (1.85 m from its Hexagon position).
- NAVON 17/18, 13/14, and the h0p10b/h0p11b and h2p5b/h2p5d pairs: duplicates.
- Other single-sensor steps in the `level-shifts` output, to triage with the same method: JAFFA_68 "1" (04-23), "6" (07-28, 08-10, 08-17, 08-23); NAVON "9" (08-09, 08-26), "5" (08-17, 08-24); SAVYON_LIVING "17" (08-26); RKL `PRISM%ATS1%r8` (07-08).

**Per-sample query (Hexagon era):** a sample belongs to a different prism if its `Easting/Northing/Height` is more than 0.5 m from the sensor's own reference position (median of a known-good window). For the live era, `ats-crossmap.ts` does the same check per device.

## 6. Proposed fix: BR-1.1 (proposal only, no code changed)

### 6.1 Bridge (`scanin-svc-mqtt-bridge`)

1. **Stable key = station + point.**
   - Map doc ID `{stationId}:{pointId}`, for example `ATS-6:h2p3f`. Keep reading the legacy `{deviceId}` docs during migration.
   - Store `atsSiteId` and `projectId` on the map doc and **require** `payload.siteId === map.atsSiteId`. Today the bridge ignores `siteId` when routing.
2. **No fallback, no auto-create into production.** In `findOrCreateAtsSensor`, remove the `findAtsSensor` (legacy `atsDeviceId` query) fallback and `createAtsSensorAndMap`. Unmatched point, site mismatch, or a map pointing at a missing or `active: false` sensor all mean the same thing:
   - `storeRawPayload(deviceId, 'unrouted-sample', payload)`
   - plus one internal integrity notice per device per day (`integrity` alert, plan §4.1)
   - and **never** a guessed or new sensor.
   - New points get mapped explicitly in the UI (`ats-live-*`), which also sets `confirmed: true`.
3. **Identity guard per sample.**
   - At map time, store `refPos: {e, n, u}`: the point's median position when it was mapped.
   - If |(e,n,u) − refPos| > 0.5 m, don't write to the sensor. Store it raw and raise a notice (`identity-mismatch`).
   - This catches B and C directly: 8.9 m, 3.2 m, 22 m. It also catches A once the frame error is large (> 0.5 m for most points in this event).
4. **Plausibility + run QA (BR-1.3/1.4)** for frame errors under 0.5 m:
   - Per-sample: jump > 50 mm vs the point's last-3-days median → `suspect: true, suspect_reason: 'implausible-jump'`.
   - Per-cycle (group by station + 45 min window): if most points shift coherently (rigid fit residual < 5 mm, |t| or rotation large), mark all samples in the cycle `suspect_reason: 'run-common-mode'` and send one notice per cycle. `ats-frame.ts` is the reference implementation.
5. **Map integrity.**
   - One sensor ↔ at most one device. Enforce it in the UI and check it in the bridge at startup (log/notice on duplicates).
   - Map edits create a `baseline-events` doc (`reason: 'mapping-fix' | 'ats-setup'`, BR-1.2).

### 6.2 Outside the bridge (needed for the same goal)

- **functions `cleanUnconfirmedSensors`:** skip sensors that are a target in `ats-device-map`, or have `dataSource: 'ats_live'`. Better: delete the map entry in the same batch so the bridge falls into the "unrouted" path.
- **`scanin-fw-ats-monitoring`:** add `cycleId`, `resectionRms`, `refsUsed` and per-reference residuals to each sample's `metadata`, so the bridge can QA per run. Add a station-side frame check: the common-mode across monitored points after resection should go to suspect, not publish. Fix duplicate and wrong taught points (§3) in the station point list.
- **Hexagon (deferred):** if it stays alive, replace `.First()` with "exactly one match, else skip and log". Out of scope per plan §5.

### 6.3 Acceptance test (from tasks.md)

Replay the 09-22 21:00Z → 09-24 03:30Z `ATS-6` payloads into a test project:
- (a) every point lands on its own sensor;
- (b) h5p2a/h5p3a and h3p2b land correctly;

- (d) h2p5a/h0p11b/h3p1a go to `ats_raw_payloads` with a notice.
