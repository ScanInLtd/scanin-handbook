**What's in**
- **A. Settings → Report Pages** (`/settings/report-pages`, card "Report Pages")
  - Upload: PDF up to 5 MB, PNG/JPG up to 20 MB. Files go to `report-pages/{pageId}/{fileName}`, with a `ReportPages/{pageId}` doc holding exactly the contract fields, plus `fileName`.
  - Each upload takes a title, tags and a default `overlayTemplate`. The upload panel shows the 2 cm / 2.5 cm margin hint.
  - The list shows image thumbnails and a PDF icon for PDFs. You can filter by tag, show archived pages, archive/unarchive, and toggle the overlay default per page. There is no hard delete.
  - `pageCount` is a best-effort count done in the browser (PDF `/Count`, falling back to counting page objects, then to 1). The backend recounts anyway.
- **B. Report editor, sensor/group (and merged)**
  - "Intro pages (after the cover)" and "Closing pages (at the end)" are picked from the non-archived library pages.
  - Pages can be dragged to reorder. Each page has an overlay choice: library default / on / off, saved as `null` / `true` / `false`.
  - A master `showExplanationPages` toggle, on by default.
  - Unknown page ids are kept and shown as "⚠️ Unknown page {id}". They are never dropped.
- **C. reportType `"merged"`**
  - Parts are picked from sensor/group configs, filtered by project (default: all, or the merged config's project).
  - Parts can be reordered; duplicates are allowed; the limit is 10. `health` and `merged` configs are blocked as parts.
  - Inactive configs are allowed as parts. An active part shows a tooltip that it also keeps running on its own schedule.
  - Each part has:
    - a period override: own / absolute date range / relative, with the part's own period shown as a hint;
    - a cover override (same `report-covers/` upload as the report-level cover);
    - a title override;
    - `includeCover` / `includeExplanationPages` toggles.
  - There is no `period` field on merged configs.
  - The list has a 🧩 icon and filter. The progress panel shows Queue › Parts › Merge › Send, `Parts partsDone/partsTotal`, `currentParts`, and a percent bar.
  - A "↻ Resume" button appears when `lastStatus == "failed"` and `lastStatusDetails.runId` is set. It sends `POST /run-report/{id}` with `{ "resume": true }`.
  - "▸ Show parts" reads `ReportRuns/{runId}` live and shows each part's status, pages, bytes and error.
  - Stop / Force cancel use the existing cancel endpoint with the merged config's id.
- **D. Rules**
  - `ReportPages`: authenticated read/write, same as `ReportConfig`.
  - `ReportRuns`: authenticated read, `write: if false`.
  - Storage `report-pages/**`: authenticated read/write, same as `report-covers/**`.
  - `reports/**` is unchanged and stays backend-write-only.

**Where the contract or the setup didn't quite fit**
1. **Merged configs also store `projectId` when a project is chosen** in the editor (optional). This is an extra field outside the contract. It's used for list search and as the default filter in the part picker. Please ignore it in the worker.
2. **`ReportRuns` "no client write" isn't actually enforced.** The Firestore catch-all `match /{document=**}` still allows any authenticated user to read and write, and Firestore rules are allow-only. This is the same known caveat as `data-integrity`, and fixing it needs the catch-all narrowed (a separate task).
3. **The deployed Firestore rules weren't the repo file.** The live ruleset had temporary open rules for the Flutter calibration app (`family_calibrations`, `device_calibrations`, `calibration_templates`, open `projects`), which weren't in git.
   - I based `firestore.rules` on the deployed source and added only the new blocks, so nothing the mobile app relies on changed.
   - The repo file now matches production.
4. **Run now on merged configs.** The orchestrator call stays open until the run finishes, so the button shows "Running…" until the snapshot listener sees a terminal status.
   - If the browser or Cloud Run drops the request, the UI says the run may still be going and points to the live status. It doesn't report an error.
   - The 600 s orchestrator timeout from the spec still applies until phase 3 raises it.
5. **The "stuck" warning waits 20 min for merged configs** (5 min for other reports), because `lastStatusTime` may not change while parts render. If you update `lastStatusTime` on every part, this can go back to 5 min.
